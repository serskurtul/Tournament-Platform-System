# RB-001: Відновлення PostgreSQL з резервної копії

| Поле | Значення |
|------|----------|
| Ідентифікатор | RB-001 |
| Операція | Відновлення бази `tournament_db` з останньої валідної копії |
| Рівень автоматизації | **1 — скриптований** (`scripts/ops/backup_db.sh`, `scripts/ops/restore_db.sh`) |
| Цільовий час виконання | ≤ 30 хв (у межах RTO 1 год, [ISD §7](../architecture/isd.md#7-експлуатаційні-процедури)) |
| Остання перевірка (restore drill) | 2026-11-22, успішно, 12/12 таблиць, 2 с ([протокол](#перевірка-restore-drill)) |

## 1. Тригер

Застосовується, коли спрацьовує один з алертів [каталогу](alerts.md) і діагностика (крок 4.1) показує, що дані втрачено або пошкоджено:

| Алерт | Коли RB-001 |
|-------|-------------|
| `TournamentDatabaseDown` (critical) | под/том БД не піднімається, PVC втрачено або дані пошкоджено |
| `TournamentApiHighErrorRate` / `TournamentApiDown` | у логах API `42P01 relation ... does not exist` або `could not read block` — схема/дані зникли |
| `TournamentDatabaseBackupStale` (warning) | не відновлення, а [розділ 7](#7-резервна-копія-не-створилась): копію не створено |

Також: помилкове масове видалення даних (заявка в L2) і планові restore drill (раз на місяць).

## 2. Передумови

- Роль L2 (SRE/DevOps): `kubectl` з правами `exec`, `scale` у namespace застосунку, або SSH-доступ до хоста docker compose.
- Доступ до сховища копій (PVC `*-db-backup` або offsite-бакет) і файл парольної фрази `BACKUP_PASSPHRASE_FILE` (сейф команди, не Git).
- Інструменти: `bash`, `sha256sum`, `gpg` (для зашифрованих копій), `psql`/`pg_restore` в образі `postgres:15`.
- Повідомлення в канал `#zvytiaha-incidents`: «Почато RB-001, API у режимі обслуговування».

## 3. Змінні

```bash
export POSTGRES_USER=postgres POSTGRES_DB=tournament_db
export DB_CONTAINER=tournament-db                   # docker compose
export BACKUP_PASSPHRASE_FILE=/secure/backup.pass   # тільки для *.gpg
NS=tournament; REL=tournament-tournament-platform   # Kubernetes
```

## 4. Покрокові дії

### 4.1 Діагностика (5 хв)

```bash
kubectl -n $NS get pods,pvc -l app.kubernetes.io/instance=tournament
kubectl -n $NS logs deploy/$REL-api --since=15m | grep -E '42P01|could not|connection refused' | tail
kubectl -n $NS exec deploy/$REL-postgres -- psql -U $POSTGRES_USER -d $POSTGRES_DB -c '\dt'
```

Якщо БД просто не стартувала, але дані цілі (PVC `Bound`, таблиці на місці), то це не RB-001: перезапусти под і перейди до верифікації.

### 4.2 Зупинити запис (2 хв)

```bash
kubectl -n $NS scale deploy/$REL-api --replicas=0         # compose: docker compose stop app client
```

### 4.3 Вибрати копію (3 хв)

```bash
ls -lt backups/ | head                                    # K8s: kubectl -n $NS exec <pod з PVC> -- ls -lt /backups
```

Береться найновіша копія з наявним `.sha256` (і `.manifest` для копій зі скрипта). Час копії = точка відновлення; дані після неї втрачаються (RPO).

### 4.4 Відновити (≈ 5–15 хв залежно від розміру)

Спершу у тимчасову базу, щоб перевірити копію, не чіпаючи поточну:

```bash
scripts/ops/restore_db.sh backups/tournament_<TS>.dump.gpg tournament_restore_check
```

Скрипт перевіряє sha256, відновлює й порівнює кількість рядків з маніфестом. Якщо `verify: row counts match manifest`, відновлюємо робочу базу:

```bash
CONFIRM=yes scripts/ops/restore_db.sh backups/tournament_<TS>.dump.gpg tournament_db
```

Kubernetes: скопіювати файл у под БД (`kubectl cp`) і виконати `pg_restore -U $POSTGRES_USER -d tournament_db --clean --if-exists --no-owner /tmp/<file>.dump`.

### 4.5 Повернути API (3 хв)

```bash
kubectl -n $NS scale deploy/$REL-api --replicas=2         # compose: docker compose start app client
```

## 5. Верифікація

```bash
curl -fsS http://<host>/health        # 200, "databaseState":"Open"
curl -fsS http://<host>/api/v1/sport | head -c 200
curl -fsS http://<host>/api/v1/tournaments?page=1 | head -c 200
```

- Частка 5xx на дашборді «ZVYTIAHA: Tournament API» повертається до 0 протягом 5 хв; алерти перейшли в `resolved`.
- `restore_db.sh` вивів `verify: row counts match manifest`.
- В інцидент-тікеті зафіксовано: використана копія, точка відновлення, втрачене вікно даних.

## 6. Відкат і ескалація

**Відкат.** Робоча база перезаписується лише після успішної перевірки у `tournament_restore_check`. Якщо після кроку 4.4 верифікація провалилась:

1. Знову зупинити API (4.2).
2. Відновити попередню копію (крок 4.3, наступний файл за часом).
3. Якщо жодна копія не проходить перевірку, лишити API зупиненим і ескалювати.

Пошкоджену базу не видаляти: `ALTER DATABASE tournament_db RENAME TO tournament_db_broken_<TS>` перед відновленням, якщо дозволяє місце.

**Ескалація:**

| Умова | Кому | Таймаут |
|-------|------|---------|
| Діагностика не дала висновку | L3 — DB-розробник (Дудко В.) | 15 хв від початку |
| Жодна копія не проходить verify | L3 + тімлід, оголосити SEV-1 | одразу |
| RTO під загрозою (> 45 хв від алерту) | тімлід → комунікація клієнтам (SLA) | 45 хв |

## 7. Резервна копія не створилась

Алерт `TournamentDatabaseBackupStale`.

```bash
kubectl -n $NS get cronjob,jobs -l app.kubernetes.io/instance=tournament
kubectl -n $NS logs job/<останній db-backup job>
kubectl -n $NS create job --from=cronjob/$REL-db-backup manual-backup-$(date -u +%H%M)
```

Верифікація: новий файл `tournament_<TS>.dump` + `.sha256` на PVC. Причини, що траплялись: заповнений PVC (збільшити `backup.size`), змінений пароль у Secret.

## Рівень автоматизації: чому 1

| Рівень | Чому не обрано |
|--------|----------------|
| 0 — ручний | Команди `pg_restore` легко переплутати (база, прапорці); ручна перевірка цілісності ненадійна |
| **1 — скриптований** | Скрипти відтворюють перевірку (sha256 + маніфест) і забороняють перезапис робочої бази без `CONFIRM=yes`. Рішення лишається за людиною |
| 2 — «одна кнопка» | Операція рідкісна й руйнівна: відновлення стирає дані після точки копії. Вибір копії й момент перемикання потребують людського рішення |
| 3 — self-healing | Автовідновлення з копії при падінні пода знищило б дані, які ще можна врятувати з тому |

Наступний крок — рівень 2 для **restore drill** (не для продакшн-відновлення): щомісячний CI-job, що піднімає тимчасовий PostgreSQL і запускає `restore_db.sh` на останній копії.

## Перевірка (restore drill)

Протокол 2026-11-22 (`docs/quality-labs/lab12/evidence/restore-drill.txt`):

1. Зашифрована копія 12 КБ, 12 таблиць у маніфесті, sha256 OK.
2. Відновлення в `tournament_drill` за 2 с, `verify: row counts match manifest (12 tables)`.
3. Спроба перезапису робочої бази без `CONFIRM=yes` відхилена з кодом 2.
