# RB-002: Відмова сховища банерів (Google Cloud Storage)

| Поле | Значення |
|------|----------|
| Ідентифікатор | RB-002 |
| Операція | Діагностика і відновлення завантаження банерів; ротація ключа сервісного акаунта |
| Рівень автоматизації | **0 — ручний** (ротація ключа виконується в консолі GCP власником проєкту; кроки в кластері — `kubectl`) |
| Походження | CAPA CA-2 за [INC-001](../incidents/INC-001.md) |
| Компонент | [сховище банерів](../architecture/legacy/storage-service.md) |

## 1. Тригер

Алерт `TournamentBannerUploadFailing` ([каталог](alerts.md)): > 50% завантажень за 15 хв завершились 5xx (≥ 3 спроби). Або скарга організатора «банер не завантажується».

## 2. Передумови

- L2: `kubectl logs/exec/rollout` у namespace застосунку.
- Для ротації ключа — L3 з роллю *Service Account Key Admin* у GCP-проєкті бакета.

## 3. Дії

1. **Підтвердити масштаб** (2 хв): частка 5xx лише на маршруті `api/v1/tournaments/{id}/image`, решта API здорова.

   ```bash
   kubectl -n $NS logs deploy/$REL-api --since=30m | grep -E 'Banner storage unavailable|Banner upload failed' | tail -5
   ```

   Після CA-1 кожен збій пише рядок рівня Error з `traceId` і вкладеним винятком Google SDK.

2. **Класифікувати причину за вкладеним винятком:**

   | У лозі | Причина | Дія |
   |--------|---------|-----|
   | `invalid_grant`, `account not found`, `401` | ключ відкликано або ротовано | крок 3 |
   | `403 ... does not have storage.objects.create` | забрали роль у сервісного акаунта | L3: повернути роль *Storage Object Creator* на бакет |
   | `Banner storage is not configured` | порожній секрет після деплою | перевірити Secret / `tournament-platform-system-secrets.json` |
   | timeout, `Name or service not known` | мережа / egress | перевірити NetworkPolicy, DNS; статус Google Cloud |

3. **Ротація ключа** (L3, 10 хв): GCP Console → IAM → Service Accounts → *Keys* → *Add key (JSON)* → оновити секрет, на який вказує `storage.existingSecret` у values чарту (PA-1) → перезапустити API (ключ читається один раз при старті).

   ```bash
   kubectl -n $NS create secret generic zvytiaha-storage --from-file=service-account.json=/secure/new-key.json --dry-run=client -o yaml | kubectl apply -f -
   kubectl -n $NS rollout restart deploy/$REL-api && kubectl -n $NS rollout status deploy/$REL-api
   ```

   Docker Compose: замінити `ServiceAccountJson` у `tournament-platform-system-secrets.json` і виконати `docker compose restart app`.

4. **Тимчасовий обхід**, поки сховище недоступне: турніри створюються без банера (поле необов'язкове; клієнт після CA-1 показує, що турнір збережено). Повідомити організаторів у каналі підтримки.

## 4. Верифікація

- Тестове завантаження від імені тестового організатора → 200 і URL `https://storage.googleapis.com/<bucket>/tournament_<id>_<guid>.png` відкривається.
- Алерт перейшов у `resolved`, SLI `banner-upload` у [slo.yaml](https://github.com/serskurtul/Tournament-Platform-System/blob/main/docs/slo.yaml) зростає.

## 5. Відкат і ескалація

- Новий ключ не працює → повернути попередній секрет (`kubectl rollout undo` не відкочує Secret: застосувати збережену копію) і ескалювати L3.
- Немає доступу до GCP-проєкту протягом 30 хв → тімлід, рішення про комунікацію (SLA `banner-upload` 97%).
- Старий ключ видалити в GCP лише після верифікації нового.
