# ADR-0001: PostgreSQL + EF Core як основне сховище

- **Статус:** Accepted
- **Дата рішення:** березень–квітень 2026 (оформлено ретроспективно 2026-11-21 за історією репозиторію: перші міграції `20260504215056_NewInitial`)
- **Учасники:** Backend (Скуртул С.), Database Engineer (Дудко В.)

## Контекст

Дані платформи сильно пов'язані: користувачі → турніри → команди → матчі (TeamA, TeamB, Winner), плюс вподобання за темами. Потрібні транзакції (реєстрація користувача з деталями й токенами, збереження результату матчу з просуванням переможця), обмеження цілісності й пошук за назвою турніру. Команда пише на .NET 9 і має досвід SQL.

## Розглянуті альтернативи

| Варіант | Плюси | Мінуси |
|---------|-------|--------|
| **PostgreSQL + EF Core (Npgsql)** | ACID, зовнішні ключі, міграції як код, безкоштовний, офіційний Docker-образ | ORM приховує SQL; потрібна дисципліна з `AsNoTracking`/проєкціями |
| SQL Server + EF Core | Найкраща інтеграція з .NET | Ліцензія для продакшну, важчий контейнер |
| MongoDB | Гнучка схема | Зв'язки й транзакції між документами складніші; дані за природою реляційні |
| SQLite | Нуль інфраструктури | Не для паралельного доступу кількох реплік API |

## Рішення

PostgreSQL 15 як єдине сховище бізнес-даних. Доступ через EF Core 9 (Npgsql), схема еволюціонує міграціями (`Infrastructure/Migrations`), які застосовує окремий init-контейнер / Helm-хук.

## Наслідки

- (+) Цілісність на рівні БД, транзакції в `AuthenticationService` і `MatchService`, відтворювана схема в будь-якому середовищі.
- (+) Однаковий стек у compose, Kubernetes (PVC) і CI.
- (−) Міграції треба застосовувати до старту нових версій API (порядок старту в [ISD §2](../isd.md#2-топологія-розгортання)).
- (−) Частина запитів обходить репозиторії й ходить прямо в `TournamentdbContext`. Це борг, який зафіксовано в ЛР-8.
