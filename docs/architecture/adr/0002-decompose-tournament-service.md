# ADR-0002: Декомпозиція `TournamentService` за відповідальностями

- **Статус:** Accepted
- **Дата:** 2026-11-21
- **Контекст рішення:** ЛР-8 «Інженерія якості» (аудит CK & MOOD)

## Контекст

`TournamentService` виріс до 935 рядків і 21 методу з п'яти бізнес-областей. Метрики: CBO = 41, WMC = 204, LCOM* = 0.82, RFC = 88. Він був головним Hotspot за ЛР-7 (CCN 41, найчастіше змінюваний файл). Точкова зміна сигнатури репозиторію ламала чотири незалежні фічі (Shotgun Surgery). Сервіс також тягнув невикористаний `IMapper` і створював генератор сітки через `new`.

## Розглянуті альтернативи

| Варіант | Плюси | Мінуси |
|---------|-------|--------|
| Залишити як є, розбити на `partial`-файли | Мінімум змін | Зв'язність і Shotgun Surgery нікуди не зникають |
| CQRS-хендлери (MediatR) на кожен use case | Максимальна згуртованість | Нова бібліотека й парадигма для всієї команди, ~20 класів |
| **Сервіси за відповідальностями з інтерфейсами й DI** | Помірна кількість класів, відома команді модель, контролер залежить від вузьких контрактів | CBO окремих класів усе ще вище за ідеал (DTO, винятки) |

## Рішення

Розбити на `TournamentManagementService`, `ParticipantService` (+ `IParticipantRoster` як єдине джерело кількості учасників), `MatchService`, `TournamentDetailsService`, `TournamentCatalogService` і спільний `TournamentStatusResolver`. Усі залежності інжектуються через конструктор як абстракції, зокрема `IBracketGenerator` / `ISeedingStrategy`.

## Наслідки

- (+) Max CBO 41 → 20, WMC 204 → 63, RFC 88 → 42. Повторний краш-тест: та сама зміна зачіпає один рядок.
- (+) `TournamentsController` залежить від п'яти вузьких контрактів.
- (−) Більше файлів і реєстрацій у DI.
- (−) Пороги CBO ≤ 8 / LCOM* ≤ 0.2 досягнуто не для всіх класів. Наступний крок — розвести `TournamentCatalogService` (LCOM4 = 2) і зменшити залежність `MatchService` від конкретних DTO.
